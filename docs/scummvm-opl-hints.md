# Hints from the ScummVM DSP AdLib (OPL) emulator

This is background from the ScummVM OPL and sibling FM projects, retained
for design context. Their channel counts, protocols and measured costs are
not F030SID results. The implemented SID design is described in
[architecture.md](architecture.md) and [dsp-kernel.md](dsp-kernel.md); current
playback limits are in [heavy-load-check.md](heavy-load-check.md).


Source: `C:\Arbeit\scummvm`, mainly `devtools/atari-falcon030/tools/foa-opl3/`
(README, `dsp/oplrt.asm`, `m68k/oplplay.s`, `opl-practical.h`, the gates) and
`devtools/atari-falcon030/docs/opl3-feasibility.md`, plus the integration in
`backends/platform/atari/dsp-opl.cpp`. The OPL project is a sibling of
F030MXDRV (it reuses its boot, BCR and SSI findings), so most of what it
learned applies here too. Everything below about SID is a hypothesis to
measure, not a result.

## What the OPL project found, and what it means for SID

### 1. Aliasing decides the output rate (important for SID)

The first practical OPL kernel ran at the codec's 32.78 kHz. Bright patches
folded back above 16.4 kHz and sounded blurry (+2.7 dB above 3 kHz, 8-15 dB in
the worst stretches against the exact kernel). Rendering at the codec's
49.17 kHz, close to the chip's own 49.7 kHz, cut that to +0.9 dB.

SID's pulse and sawtooth are not band-limited at all and the real chip's
output rate is ~1 MHz. Expect the same or worse. The scaffold must not assume
32.78 kHz (F030MXDRV's rate) is enough: plan for 49.17 kHz, and consider
cheap band-limiting of the saw/pulse edges.

Rates and budgets used by the OPL work (calibrated Hatari, 16.04 MIPS DSP):

| Output rate | DSP cycles per frame |
| --- | ---: |
| 24.585 kHz | ~652 |
| 32.780 kHz | 489.4 |
| 49.170 kHz | 326.3 |

SID has three voices (the OPL kernel measured ~55 cycles per operator when
exact, and 4-12 per frame per operator when block-rate), so three voices plus
filter looks affordable even at 49.17 kHz. That is the opposite of OPL's
exact kernel (209% of budget), and is the reason SID may be able to afford a
per-sample envelope and filter. Measure before relying on it.

### 2. Exact vs practical kernels, with a bit-exact host reference

OPL path: Nuked-OPL3 (chip model) -> `opl-kernel.h` (exact, written in 24-bit
DSP-friendly integer arithmetic, bit-exact against Nuked, 19.3 M samples, 0
mismatches) -> `oplrt.asm` (DSP, compared word-for-word with a host
"practical" reference) -> perceptual comparison of practical vs exact.

For SID: reSID as the chip model; a C reference written in 24-bit integer
arithmetic (flat arrays, no division, no pointers); the DSP code is
transliterated from it and gated word-for-word. Do this before writing DSP
code that is hard to debug.

### 3. Block-rate control is a design choice, and 32 frames cost more than 48

The OPL kernel updates envelopes/LFOs once per block and applies register
writes at the start of the containing block (up to one block early). Blocks
went 64 -> 48 -> 32 frames: key-on lead shrank 1.30 -> 0.65 ms but per-frame
cost rose 175.7 -> 217.6 cycles because per-block boundary work grows with
the block count.

SID caveat: the classic "digi" technique writes `$D418` (volume) at
sample rate and register writes are audible at cycle level (test bit,
hard-restart, gate timing). Block-aligned writes will break digis and
tightly timed attacks. The DSP should support timestamped, sample-aligned
write events (the OPL doc lists event-aligned splits as a future option; the
F030MXDRV kernel already has an ordered mid-block event FIFO), at least for
`$D418`.

### 4. Decode registers on the 68030, not the DSP

OPL's `Decoder` turns each register write into a few parameter words for the
DSP's operator/channel records, emitted only when they change and derived
once at block end (a note touches several registers that share derived
values). Cost on the host: ~1 us per write. The DSP boundary pass is then
free of register logic.

For SID: derive frequency increments, pulse width compares, ADSR rate
periods and filter coefficients on the 68030 (or once per block), and send
parameter words. Keep the register file in the DSP only if reads (`$1B`
OSC3, `$1C` ENV3) must come from live DSP state.

### 5. Memory map and ROMs

- OPL fit its waveform ROM in 512 words by storing a 256-entry quarter
  log-sine plus an exp table and rebuilding indices/signs by arithmetic.
  Tables are generated by `generate-tables.py` (closed form) and gated
  against the reference. SID analogues: the 6581/8580 DAC curves and the
  combined-waveform tables (these are not closed form and are large; they come
  from reSID's sampled tables) and the filter cutoff curve.
- Use external X/Y SRAM freely: with `movep #0,x:m_bcr` the Falcon's DSP SRAM
  has zero wait states (reset leaves fifteen). Hatari still charges extra when
  one instruction touches two external spaces, so split a parallel
  external-X plus external-Y move into two instructions.
- Hot loops in internal P ($0080-$01ff); everything else external. The OPL
  program is 1,608 words, with 437 in internal P. The oplrt memory map header
  (top of `dsp/oplrt.asm`) is a good template for an audited map.
- 24-bit trick: keep phase shifted so the table index is the top bits and use
  a multiply by a pre-doubled constant instead of repeated one-bit shifts.
  SID's 24-bit phase accumulator maps naturally onto the DSP word.
- Parallel X/Y moves were an untapped optimization in the exact OPL loop
  (estimated 40-45 vs 56 cycles/operator); use them from the start.

### 6. Transport: ring + interrupt + READY handshake + lateness counting

Stream mode owns the SSI: a ring of two 768-frame periods (15.62 ms) in
external X, transmitted under interrupt via a pointer register; each period
arrives from the host as events plus PCM; the DSP acknowledges before
rendering (with period and late counters in the ack), so the host stays one
period ahead; an unready period repeats and is counted.

Hard-won details worth copying:

- Opening: wait until the transmitter has just entered the ring half about to
  be rendered, so the first period gets a whole half and no late period.
- A host that stops sending renders nothing, so a "late" check done only after
  rendering reads 0 during a stall. Watch the transmitter from every wait. A
  gate that withholds refills for 0.995 s must read ~62 late periods.
- `CMD_MARGIN` reports the tightest period's slack; "no late period" alone
  says nothing about how close it came. Wire an equivalent in early.
- READY is answered on the host's next timer tick (up to 1 ms in ScummVM);
  that latency eats slack. F030MXDRV's Timer-A-driven delivery and early
  accept (`DSP_CMD_EARLY_ACCEPT`) address the same problem.
- Port C pins must be set to SSI function (`movep #$1f8,x:m_pcc`) and the
  crossbar must be armed after `Devconnect`; the inherited `ratetest.tos`
  checks this on real hardware.
- A payload with no PCM means silence and must clear interpolation history,
  otherwise the next sample interpolates from stale data (loud transient).
  Same for a SID that is stopped and restarted: reset the filter/voice state.

### 7. Capture and test methodology

- Record the real driver's register stream headlessly with a deterministic
  virtual clock so repeated runs are byte-identical; keep the capture build
  in a separate tree so no object is linked by accident. For SID, capture the
  `$D400-$D41C` writes with cycle timestamps from a 6502/PSID run
  (libsidplayfp or the project's own core), and store compact traces in
  `tests/traces/`.
- Measure traffic before sizing transport: OPL's mean was 204 writes/s but the
  busiest callback carried 129; sizing on the mean would have been wrong by
  ~160x. SID players call play() at 50/60 Hz (or CIA multispeed), writing ~25
  registers per call, so expect the same burstiness.
- Result files (`*-results.json`) and one gate script per claim keep the
  README honest. Model F030SID's gates on `kernel-gate.py`,
  `rt-bench-gate.py`, `rt-stream-gate.py`, including the starved-host and
  stress scenarios.
- Profile the DSP with Hatari's profiler attributed by code range; report
  stages / boundary / loaders / emit separately.
- Be explicit about limits: Hatari models zero wait states and is
  instruction-accurate rather than cycle-accurate; nothing is proven on
  hardware until run on a physical Falcon.

### 8. Do not conflate "approximate" with "block-rate"

The OPL write-up separates approximations that block processing forces
(envelope retiming) from ones that are choices (its rhythm noise stepping is
a noise-clock approximation, not a block-rate necessity). Keep that
distinction when listing SID deviations: a 15-bit noise LFSR can be exact,
the 15-bit ADSR rate counter and its exponential-decay breakpoints can be
exact, even if the waveform DAC and filter are approximations.

## Suggested changes to the F030SID plan

1. Target 49.17 kHz first (prescale 1), fall back to 32.78 kHz only after
   listening tests on bright saw/pulse material.
2. Write the 24-bit integer C reference and the reSID comparison gate before
   the DSP kernel (roadmap step 2 in `architecture.md`).
3. Put timestamped write events in protocol v2 from the start, not an
   afterthought; give `$D418` sample accuracy.
4. Parameter derivation on the 68030; DSP holds per-voice state records in
   external X with phase fractions in the matching Y addresses (the OPL
   layout).
5. Add `CMD_MARGIN`/late-period counters to the protocol alongside
   `START_AUDIO`.
6. Reuse oplrt's SSI ring/interrupt and `Dsp_ExecBoot` + `BCR=0` bring-up
   (`dsp/oplrt.asm` near the labels at `p:$2000` and the `m_crb`/`m_cra`
   writes around lines 1803-1837).

## After the kernel existed (2026-10-04)

A second reading of `oplrt.asm` against `src/dsp/sid.asm.in`, prompted by real
tunes costing 100-165% of the frame (docs/player.md). Read from the code and the
result files; the gains are estimates, nothing below has been built.

From the OPL kernel to the SID kernel, all exact:

1. **The stream loop.** oplrt emits in a tight `do` with pointers and checksum
   in registers and polls the host once per block: 7.3-7.8 cycles per frame
   ("Emit, clear, events" in its README). `stream_step` pays about 50: an HSR
   test, a horizon test, a nine-instruction checksum over four words, `G_WP` and
   `G_SUM` through long addresses and the `G_HREM` update, per frame, from
   external P. Bounding the run once by `min(room, horizon / 21)`, polling HSR
   every few frames and summing the chip word only should return 20-30 cycles.
2. **Noise.** oplrt advances a silent noise register lazily (`catch_up_noise`)
   and steps it several clocks at once through byte tables (`noise_jump`). The
   SID kernel shifts every voice's register at every bit-19 edge, noise selected
   or not, and gathers the eight output bits with `jclr` chains: about 88 cycles
   a step, half of it the gather. Count the pending steps of a voice without
   noise and catch up on the control write; gather with three 256-entry tables.
3. **Silent voices.** oplrt skips a silent channel and keeps its phase running.
   A SID voice released to envelope 0 still runs its waveform handler and every
   polyBLEP edge; a null handler from `es_zero` would save 15-25 cycles and the
   edges (check that the envelope DAC word at 0 is exactly 0).
4. **Envelope hold.** `eh_hold` is visited every rate period, every frame at
   rate 0. Advance `S_REM` by a multiple of the period and reduce it on the next
   write instead.
5. **Transport.** oplrt's events are two words; a SID write is three, and a
   cutoff write becomes nine queue entries. One multi-word coefficient entry.
6. **A practical tier, gated as oplrt's is.** Block-rate envelopes do not carry
   over (the countdown envelope is already cheap when idle); the candidates are
   the polyBLEP correction (a reciprocal multiply for its `DIV`, or two points
   instead of four), with the reference changed to match so the gates stay exact.
7. **32.78 kHz** as a fallback build: 489 cycles per frame; the aliasing of the
   paths that are not band-limited is unmeasured.

Overload: neither kernel sheds load. oplrt replays the stale half and counts
every one from every wait (`track_halves`); the SID stream replays about a ring
and its count is low (see docs/player.md). A doubled frame (n = 40/41, written
twice) when the fill is low would be the SID's equivalent of extension periods.

From the SID kernel to the OPL kernel: `op_boundary` recomputes the gains of
every keyed operator on every block and split; a per-operator "unchanged"
countdown, as the SID frame uses, would cut its 23-26 cycles per frame. oplrt's
checksum is an order-insensitive sum; `3 * sum + word` is stronger. Its status
word wraps the late count at 4096. Its README still describes block-boundary
writes and noise "stepped twice a frame" where the code is sample-timed; section
3 above inherited the first.
